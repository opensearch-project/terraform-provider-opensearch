# OpenSearch Terraform Provider Test Suite

> Test suite for the official OpenSearch Terraform provider using native HCL and `terraform test`.
> 
> Each `.tftest.hcl` file declares its own `provider "opensearch"` block so Terraform test can initialize the provider when running alternate modules. The Makefile generates `tests/terraform.auto.tfvars` with the correct URL, username, and password for the Compose test cluster.

## Test Coverage

See [`TEST_COVERAGE.md`](TEST_COVERAGE.md) for a detailed matrix of resource coverage, test categories (Minimal / Full / Update / Invalid), and known gaps.

## Quick Start

Testing is run through the root Makefile, which automates provider build/configuration, container lifecycle, health checking, Terraform variable generation, integration data setup, and test execution.

### Running All Tests

```bash
# Run all tests with automatic port allocation
make tf-test-local

# Run with verbose output
make tf-test-local TF_TEST_ARGS="-verbose"
```

### Running Specific Tests

```bash
# Filter by test file
make tf-test-local TF_TEST_ARGS="-filter=tests/opensearch_index.tftest.hcl"

# Filter by run block
make tf-test-local TF_TEST_ARGS="-filter=tests/opensearch_index.tftest.hcl -run=create_index_minimal"
```

### OpenSearch Version Testing

Run one OpenSearch version per invocation. `OS_VERSION` selects the Compose image:

```bash
make OS_VERSION=2 tf-test-local
make OS_VERSION=3 tf-test-local
make OS_VERSION=3 tf-test-local TF_TEST_ARGS="-filter=tests/opensearch_index.tftest.hcl"
```

## Project Structure

```
├── docker-compose.yml          # Local OpenSearch (security enabled)
├── providers.tf               # Declares input variables (url, username, password)
├── modules/                   # Reusable resource modules
│   └── {resource}/           # One module per resource type
│       ├── main.tf
│       ├── variables.tf
│       └── outputs.tf
├── tests/                     # Test files (*.tftest.hcl)
│   ├── {resource}.tftest.hcl
│   └── terraform.auto.tfvars # Auto-generated by Make (ephemeral)
├── fixtures/                  # Sample policies, mappings, data
└── scripts/                   # setup, teardown, helpers
```

## Docker Compose

- **Image**: `${OPENSEARCH_IMAGE:-opensearchproject/opensearch:2}` (controlled via `OPENSEARCH_IMAGE` environment variable)
- **Security**: Enabled via demo certificates (security plugin active)
- **Ports**: 9200 (REST API HTTPS), 9300 (transport)
- **Credentials**: `admin` / `myStrongPassword123@456` (for testing only)
- **Health**: Wait for `_cluster/health` returning `status`

## Testing Conventions

### Test File Pattern
```hcl
# tests/index.tftest.hcl
run "create_minimal" {
  module { source = "./modules/index" }
  variables { name = "test-minimal" }
  assert { condition = opensearch_index.this.name == "test-minimal" }
}

run "update_settings" {
  module { source = "./modules/index" }
  variables {
    name = "test-minimal"  # Same name, updates in place
    number_of_replicas = 1
  }
}

run "destroy" {
  # Implicit destroy happens after last run
}
```

## Module Design
- **inputs**: Resource-specific parameters with sensible defaults
- **outputs**: Expose resource IDs and computed values for assertions
- **lifecycle**: Test modules should handle create/update/destroy cleanly

### Module Types
- **Typed modules**: Variables map directly to provider resource arguments (e.g., `opensearch_index`, `opensearch_role`, `opensearch_cluster_settings`). Enables granular assertions.
- **JSON-body modules**: Accept an opaque `body` string for complex resources (e.g., `opensearch_monitor`, `opensearch_ism_policy`, `opensearch_component_template`). Useful for provider resources with nested or highly dynamic schemas.

### Test Categories
1. **Minimal**: Required fields only
2. **Full**: All configurable fields
3. **Update**: Modify existing resources
4. **Invalid**: Expect errors (negative tests)

## Provider Configuration

Each `.tftest.hcl` file declares its own `provider "opensearch"` block so Terraform test can initialize the provider when running alternate modules:

```hcl
# tests/index.tftest.hcl
provider "opensearch" {
  url      = var.opensearch_url
  username = var.opensearch_username
  password = var.opensearch_password
  insecure = true
}

run "create_minimal" {
  module { source = "./modules/index" }
  variables { name = "test-minimal" }
  assert { condition = opensearch_index.this.name == "test-minimal" }
}
```

The `tf-test-vars` Make target generates `tests/terraform.auto.tfvars` with the correct URL and credentials for the Compose container. Terraform test auto-loads this file because it lives in the same directory as the `.tftest.hcl` files.

### Manual Variable Configuration

If running `terraform test` directly without Make, provide variables via one of:
- `tests/terraform.auto.tfvars` (auto-loaded by Terraform test)
- `tests/terraform.tfvars` (auto-loaded by Terraform test)
- `-var` flags on the command line
- `TF_VAR_*` environment variables

```bash
# Example manual tfvars for fixed-port testing
cat > tests/terraform.auto.tfvars <<EOF
opensearch_url      = "http://localhost:9200"
opensearch_username = "admin"
opensearch_password = "myStrongPassword123@456"
EOF
```

## Local Development

### Using Local Provider Build

The `tf-test-local` target builds the provider, generates `.dev.terraformrc`,
starts the selected OpenSearch version, loads test data, runs Terraform tests,
and cleans up the container:

```bash
make tf-test-local
make OS_VERSION=3 tf-test-local
make OS_VERSION=2 tf-test-local TF_TEST_ARGS="-filter=tests/opensearch_monitor.tftest.hcl"
```

The generated `.dev.terraformrc` uses a `dev_overrides` directory pointing to
the repository root, where `dev-build` places the provider binary.

### Using Global Local Provider Build

Alternatively, create `~/.terraformrc` for all projects:

```hcl
provider_installation {
  dev_overrides {
    "opensearch-project/opensearch" = "/path/to/provider/binary"
  }
  direct {}
}
```

### Running Single Tests
```bash
# Filter by test file
terraform test -filter=tests/role.tftest.hcl

# Filter by run block
terraform test -filter=tests/role.tftest.hcl -run=create_admin_role
```

## Common Gotchas

- **Security initialization**: OpenSearch takes 30-60s to start with security plugin
- **Index names**: Cannot create index that already exists; use random prefixes
- **ISM policies**: Must wait for managed index before attaching policy
- **Snapshots**: Requires registered repository (test with fs type)
- **Roles**: Changes to built-in roles may require cluster restart

## Integration Test Scenarios (Implemented)

> All 4 scenarios are implemented and run automatically as part of `make tf-test-local`.

### Running Integration Tests

Integration test files live in `tests/` alongside unit tests and are automaticallydiscovered by Terraform test:

```bash
# Run all tests (unit + integration)
make tf-test-local

# Run a specific integration test file
terraform test -filter=tests/log_ingestion_pipeline.tftest.hcl
```

### Pre-Populating Test Data

Some integration tests require indexed documents before provider resources can be created (e.g., anomaly detection detectors). The `tf-test-data` Make target runs `script/setup-integration-data.sh` after OpenSearch is healthy but before Terraform tests execute. This helper creates indices and ingests documents via the OpenSearch REST API using `curl`.

### Scenario 1: Log Ingestion Pipeline
**File:** `tests/log_ingestion_pipeline.tftest.hcl` *(implemented)*

Tests complete log ingestion workflow with ISM:
1. Component template (common log mappings)
2. Index template (composable with component)
3. ISM policy (Hot→Warm→Delete lifecycle with `ism_template`)
4. Ingest pipeline (log enrichment)
5. Bootstrap index with alias (`integration-log-application-000001`)
6. Security role (`integration-log-reader`)

**Resources tested:** 6 resources in dependency order

### Scenario 2: Security Monitoring & Alerting

3. Monitor (failed login threshold)
4. Security analyst role
5. Analyst user account
6. Roles mapping

**Resources tested:** 6 resources with alerting integration

4. Dashboard objects (index pattern saved object)
5. Tenant-specific roles
6. Users with attributes

4. Audit config (compliance logging)
5. Component template (compliance metadata)
